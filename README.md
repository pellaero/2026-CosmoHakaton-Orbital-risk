# Анализ рисков ВКД на МКС

Исследовательский прототип поддержки решений для аналитика наземной группы планирования внекорабельной деятельности (ВКД).
Кейс «Прогнозирование внешних рисков и планирование ВКД на МКС», КосмоХакатон 2026.

Сервис сам получает открытые данные, рассчитывает положение МКС и оценивает окна ВКД по **четырём механизмам воздействия**:

| # | Механизм | Что оценивается | Данные |
|---|---|---|---|
| 1 | Космическая погода | Геомагнитная буря (Kp) и солнечное протонное событие (протоны ≥ 10 МэВ) | GFZ Potsdam, NOAA SWPC, GOES |
| 2 | Орбитальная обстановка | Сближения МКС с отслеживаемыми объектами (MMOD) | CelesTrak SOCRATES |
| 3 | Освещённость | Доля времени окна в тени Земли | Орбита МКС (SGP4) + эфемериды JPL DE421 |
| 4 | Солнечные блики | Угол между направлением на Солнце и на Землю из точки МКС | Орбита МКС (SGP4) + эфемериды JPL DE421 |

Механизмы 3 и 4 — собственный расчёт команды по траектории станции. Механизмы 1 и 2 — интерпретация внешних наблюдений и прогнозов.
Сервис не принимает решения о допуске к ВКД: это делают уполномоченные специалисты.

---

## Быстрый старт — одна команда

```bash
docker compose up -d --build
```

Откройте **http://127.0.0.1:7860**.

Первая сборка занимает 2–5 минут: скачивается образ Python, зависимости и эфемериды DE421 (~17 МБ). Следующие запуски — секунды.

## Подробная инструкция запуска

### 1. Что нужно

| Требование | Зачем | Как проверить |
|---|---|---|
| Docker Desktop (macOS / Windows) или Docker Engine + Compose v2 (Linux) | Сборка и запуск контейнера | `docker compose version` |
| Интернет | Сборка образа, загрузка данных NOAA, GFZ, CelesTrak | — |
| Свободный порт 7860 | Веб-интерфейс | `lsof -i :7860` должен ничего не вывести |

Ключи API, регистрация и секреты **не нужны**: все источники открытые.

### 2. Запуск

1. Запустите Docker Desktop и дождитесь статуса «Engine running».
   Проверка: `docker info` выполняется без ошибки.
2. Перейдите в папку проекта:
   ```bash
   cd eva_docker
   ```
3. Соберите и запустите:
   ```bash
   docker compose up -d --build
   ```
   Команда собирает образ `eva-app` по `Dockerfile` и запускает контейнер `eva-app` в фоне.
4. Дождитесь старта (5–10 секунд после сборки) и проверьте:
   ```bash
   docker compose logs -f
   ```
   Готовность — строка `Running on local URL: http://0.0.0.0:7860`. Выйти из логов: `Ctrl+C` (контейнер продолжит работать).
5. Откройте **http://127.0.0.1:7860**.

### 3. Проверка, что всё работает

1. Оставьте значения по умолчанию (исторический режим, 2024-05-11, окна 12:00 и 18:00, длительность 6 ч).
2. Нажмите «Запустить анализ».
3. Ожидаемый результат: окно 1 — **70/100** (протоны 45.2 pfu и Kp 8.7), окно 2 — **30/100** (Kp 7.7), рекомендация — окно 2.
4. Нажмите «Прогноз на 3 дня», затем «Запустить анализ». Расчёт перебирает 49 окон и занимает 10–40 секунд.

### 4. Управление

| Действие | Команда |
|---|---|
| Остановить | `docker compose down` |
| Запустить снова | `docker compose up -d` |
| Пересобрать после изменений кода | `docker compose up -d --build` |
| Логи | `docker compose logs -f` |
| Статус | `docker compose ps` |

Контейнер перезапускается автоматически после перезапуска Docker (`restart: unless-stopped`).
Порт открыт только на `127.0.0.1`. Чтобы открыть доступ из локальной сети, замените в `docker-compose.yml` строку порта на `"7860:7860"`.

### 5. Запуск без Docker

Нужен Python 3.12.

```bash
python3.12 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python eva_app.py
```

Откройте http://127.0.0.1:7860. При первом запуске Skyfield скачает `de421.bsp` в текущую папку.

### 6. Частые проблемы

| Симптом | Причина | Решение |
|---|---|---|
| `Cannot connect to the Docker daemon` | Docker не запущен | Запустите Docker Desktop |
| `port is already allocated` | Порт 7860 занят | Остановите другой процесс или поменяйте порт в `docker-compose.yml`, например `"127.0.0.1:8080:7860"` |
| `container name "/eva-app" is already in use` | Остался контейнер от ручного `docker run` | `docker rm -f eva-app`, затем снова `docker compose up -d --build` |
| В отчёте «данные недоступны», в логах `[КЭШ] ... Переход на снапшот` | Нет доступа к источнику или таймаут | Проверьте интернет и отметьте «Принудительно обновить кэш» |
| (macOS, без Docker) `pip` падает с `Symbol not found: _XML_SetAllocTrackerActivationThreshold` | Сломанная связка Homebrew-Python и системной libexpat | Используйте Docker или `export DYLD_LIBRARY_PATH=/opt/homebrew/opt/expat/lib` |

## Как пользоваться

| Сценарий | Действия |
|---|---|
| **Сравнить два окна** | Выберите режим и дату, задайте начало окна 1 и окна 2 (UTC) и длительность 1–8 ч → «Запустить анализ» |
| **Разбор исторического события** | Режим «Исторический (Replay)», дата в мае–июне 2024 → «Запустить анализ» |
| **Найти лучшее окно** | «Прогноз на 3 дня» → «Запустить анализ». Перебираются старты с шагом 1 ч на 48 ч вперёд от 00:00 UTC сегодня |
| **Изменить план** | Сдвиньте начало или длительность и запустите анализ снова: всё пересчитывается |
| **Сохранить результат** | После расчёта в карточке «Сохранённый отчёт (JSON)» появится файл для скачивания |
| **Обновить данные** | Отметьте «Принудительно обновить кэш» и запустите анализ |

Результат запроса:
- **отчёт по окнам**: интегральный риск команды, риск простого подхода, минуты на свету и в тени, блики, сближения, критические флаги и предупреждения;
- **рекомендация** и **сравнение с простым подходом (T5)**;
- **доказательная база** по каждому сработавшему фактору: значение, порог, статус `CRITICAL` / `WARNING` / `UNKNOWN`, механизм, физический смысл;
- **график Kp** с порогами Kp = 5 и Kp = 7 и окнами, окрашенными по уровню риска;
- **JSON-отчёт** и **статус кэша** с давностью каждого набора данных.

| Величина | Источник | Единицы / формат | Частота и горизонт | Кэш | Ограничения |
|---|---|---|---|---|---|
| Орбитальные элементы МКС (NORAD 25544) | CelesTrak GP, `gp.php?CATNR=25544&FORMAT=tle` | TLE | Обновляется несколько раз в сутки, только актуальный набор | 12 ч | Архив прошлых TLE не запрашивается (см. ограничения Т2) |

| Kp-индекс, текущий и прогноз | NOAA SWPC, `noaa-planetary-k-index-forecast.json` | безразмерный 0–9, шаг 3 ч | Наблюдение, оценка и прогноз на ~3 суток | 30 мин | Поле observed / estimated / predicted пока не выводится |
| Поток протонов ≥ 10 МэВ | NOAA SWPC, GOES primary, `integral-protons-7-day.json` | pfu (частиц·см⁻²·с⁻¹·ср⁻¹), шаг 5 мин | Только последние 7 суток | 15 мин | Геостационарная орбита — прокси-показатель для МКС; для дат старше 7 суток данных нет |
| Сближения с отслеживаемыми объектами | CelesTrak SOCRATES, `sort-minRange.csv` | TCA (UTC), дистанция км, относительная скорость км/с | Прогноз на 7 суток вперёд | 1 ч | Только каталогизированные объекты; пристыкованные корабли (относительная скорость < 0.01 км/с) отфильтрованы |
| Положение Солнца и Земли | JPL DE421 через Skyfield | км / а.е. | 1900–2050 | в образе | — |

## Модель оценки

**Пороги** (`THRESHOLDS`): Kp ≥ 7 — критично, Kp ≥ 5 — предупреждение; протоны > 10 pfu — критично (порог шкалы S1 NOAA); сближение < 5 км; тень > 50 % окна; угол бликов < 5°.

**Интегральный риск окна** (0–100) — сумма вкладов механизмов:

| Условие в окне | Вклад | Статус |
|---|---|---|
| Протоны > 10 pfu | +40 | CRITICAL |
| Kp ≥ 7 | +30 | CRITICAL |
| 5 ≤ Kp < 7 | +15 | WARNING |
| Сближение < 5 км с TCA внутри окна | +20 | CRITICAL |
| Тень > 50 % окна | +10 | WARNING |
| Угол бликов < 5° | +10 | WARNING |
| SOCRATES недоступен | 0, отдельный флаг | UNKNOWN |

Уровни: < 40 — низкий, 40–69 — средний, ≥ 70 — высокий.

**Простой подход (baseline)**: риск 100, если максимальный Kp в окне ≥ 5; 0 — если меньше; 50 — если данных Kp нет.

**Освещённость и блики** рассчитываются каждые 5 минут окна: положение МКС по SGP4 → `is_sunlit` по эфемеридам DE421 → доля тени. Угол бликов — угол между векторами «МКС → Солнце» и «МКС → центр Земли».

**Выбор окна**: из окон с риском < 40 берётся окно с минимальным риском. Если таких нет, берётся минимальный риск среди всех окон. Равные риски в режиме двух окон дают вывод «Окна равнозначны».

**Выгрузка JSON** содержит режим, версию алгоритма, дату, длительность, время начала окон, риск команды, базовый риск, доказательную базу по факторам, рекомендацию и метку времени расчёта.

## Соответствие критериям оценки

Для каждого критерия сначала указано, чем решение закрывает требование и где это видно, затем — ограничения текущей версии.
Критерии О1, О2, Т1 и Т4 прямо требуют честно называть ограничения, поэтому они приведены полностью.

### Отраслевые эксперты

#### О1. Выбор факторов и пользовательская задача (0–8)

**Реализовано**
- Четыре **разных** механизма воздействия, а не несколько показателей одного: космическая погода (геомагнитная буря и радиационная обстановка), MMOD, освещённость, блики. Постановка требует минимум два, включая космическую погоду.
- Для каждого фактора в доказательной базе указана связь с ВКД: протоны — радиационная безопасность; Kp — нарушения навигации и связи; MMOD — сближения; тень — тепловой режим скафандра; блики — ослепление визора.
- Сценарий построен вокруг задачи аналитика: он задаёт конкретные окна (начало + длительность) и получает оценку именно для них.
- Пригодность данных описана в таблице источников выше: единицы, частота, горизонт, ограничения.

**Ограничения**
- Протоны GOES измеряются на геостационарной орбите — это прокси-показатель; пересчёт на орбиту МКС и в дозу не выполняется.
- SOCRATES покрывает только каталогизированные объекты и не даёт вероятности попадания мелкого фрагмента.
- Тень сама по себе не опасность; в модели это условие работ, связанное с тепловым режимом, с умеренным весом +10.

#### О2. Интерпретация обстановки (0–8)

**Реализовано**
- Внешние измерения (Kp, протоны), условия на траектории (тень, блики по SGP4) и оценка последствий (статус и пояснение) разделены в доказательной базе полем `mechanism`.
- Уровни угрозы применяются по единым порогам `THRESHOLDS` для всех режимов.
- Недоступность SOCRATES не превращается в «безопасно»: выставляется статус `UNKNOWN` и отдельное предупреждение «риск не оценен».
- В режиме двух окон рекомендация формулируется как сравнение («Окно 2 имеет меньший интегральный риск»), а не как заявление о безопасности.

**Ограничения**
- В режиме прогноза вывод звучит как «Алгоритм команды нашел безопасное окно». Это стоит заменить на «окно с наименьшим риском» (формулировка, а не логика).
- Если нет данных Kp или протонов для окна (например, протоны для дат старше 7 суток, кроме 11.05.2024), фактор молча не учитывается, и риск может получиться 0/100 без флага `UNKNOWN`. Для MMOD это уже обрабатывается; для Kp и протонов нужно добавить такой же флаг.

#### О3. Сравнение и рекомендация по окну (0–8)

**Реализовано**
- Сравнение двух окон **одинаковой длительности**, заданных пользователем, и автоматический перебор 49 стартов с шагом 1 ч (`compare_windows_dynamic`).
- Пересчёт при изменении плана: сдвиг начала и длительность (слайдер 1–8 ч) — отдельные параметры, каждый запуск считается заново.
- Видно, какие факторы повлияли на выбор: флаги и доказательная база по каждому окну, окна подсвечены на графике Kp.
- Равнозначные окна обрабатываются явно: «Окна равнозначны по уровню риска».

**Ограничения**
- Не показывается длительность пересечения окна с неблагоприятными условиями (только максимум за окно) и в какие часы окна сработал фактор.
- Нет отдельного вывода «оснований для выбора недостаточно», когда данных по ключевому фактору нет.
- Период поиска фиксирован (48 ч от 00:00 UTC), а не задаётся пользователем; постановка требует до 24 ч.

#### О4. Объяснения и доказательства (0–8)

**Реализовано**
- Для каждого сработавшего фактора: значение, порог, статус, механизм и физическое объяснение (`factors_proof`). Всё это попадает в интерфейс и в JSON.
- Команда отделена от внешних данных: «Интегральный риск (команда)» показан рядом с «Базовый подход (только Kp)».
- Для каждого набора данных в коде хранятся источник и тип данных («Наблюдение (Факт)», «Внешний прогноз», «Локальный кэш»).

**Ограничения**
- Источник и тип данных (`kp_src`, `kp_type`, `prot_src`, `tle_src`) вычисляются, но пока не выводятся в интерфейс и JSON.
- Нет ссылки на первоисточник и времени публикации записи.
- В режиме двух окон доказательная база сохраняется в JSON, но в текстовом отчёте выводится только в режиме прогноза.

#### О5. Удобство работы (0–8)

**Реализовано**
- Пользователь сам задаёт окна, длительность и дату, переключает режим (исторический / текущий / прогноз на 3 дня).
- Временная картина — интерактивный график Plotly; сравнение окон — карточки с цветовой и символьной разметкой уровня риска (▲ / ◆ / ✓ / ○).
- Результат сохраняется в JSON и скачивается из интерфейса.
- Статус длительной операции показывает Gradio; ошибки выводятся в отчёт с текстом исключения; статус кэша показывает давность каждого набора данных.
- Адаптивная вёрстка (десктоп и телефон), единый пользовательский путь в веб-сервисе.

**Ограничения**
- Нет кнопки перехода к первоисточнику.
- Сообщение об ошибке технологическое (traceback), а не пользовательское.

#### О6. Презентация решения (0–5)

Оценивается по выступлению. Для демонстрации подготовлен сценарий: 11.05.2024, экстремальная буря G5 — простой подход отменяет оба окна (100/100), алгоритм команды различает их (70 против 30) благодаря учёту протонов по времени.

#### О7. Дополнительные функции (0–5)

- **Автоматический поиск лучшего окна** на 48 ч вперёд — прямо назван в «Развитии решения». Польза: аналитик получает кандидата без ручного перебора.
- **Четыре механизма вместо двух обязательных**, два из них — собственный расчёт по орбите (освещённость, блики).
- **Плавная деградация**: кэш с TTL на каждый источник, снапшот, статус кэша в интерфейсе.
- **Фильтр пристыкованных кораблей в SOCRATES**: без него «Союз МС-29» (сближение 6 м, относительная скорость 0) давал бы критический флаг MMOD в любом окне.
- **Запуск одной командой** в Docker.

### Технические эксперты

#### Т1. Получение и подготовка данных (0–7)

**Реализовано**
- Автоматическое получение текущих (NOAA SWPC, CelesTrak) и архивных (GFZ Potsdam) данных без ручных шагов.
- Происхождение, единицы, частота и ограничения описаны в таблице источников.
- Время приводится к UTC (`pd.to_datetime(..., utc=True)`); нечисловые значения отбрасываются (`errors="coerce"`); в SOCRATES фильтруются записи не по МКС и пристыкованные объекты.

**Ограничения**
- Нет явной обработки дублей и разных частот (Kp — 3 ч, протоны — 5 мин): используется максимум за окно.
- Результат не прослеживается до конкретной исходной записи (нет её времени и идентификатора в отчёте).

#### Т2. Орбита и пространственно-временная согласованность (0–6)

**Реализовано**
- Положение МКС рассчитывается по TLE моделью SGP4 (Skyfield `EarthSatellite`) с шагом 5 минут, в шкале времени UTC Skyfield.
- Орбита используется в анализе, а не для картинки: освещённость (`is_sunlit`) и блики считаются по траектории на интервале окна.
- Эпоха TLE выводится в описании источника («CelesTrak (эпоха YYYY-MM-DD)»).

**Ограничения**
- Для исторических дат используется **актуальный** TLE CelesTrak или синтетический снапшот. Постановка прямо запрещает подменять историческую орбиту современной. Нужен архив TLE за май–июнь 2024 (Space-Track GP_HISTORY или сохранённые копии CelesTrak).
- Эпоха и давность TLE не выводятся в интерфейс.

#### Т3. Методы оценки и прогноза (0–10)

**Реализовано**
- Воспроизводимая детерминированная логика: пороги в `THRESHOLDS`, веса в `calculate_advanced_risk`, версия в `ALGORITHM_VERSION`.
- Собственный расчёт влияния на окно: доля тени и угол бликов по траектории МКС.
- Kp (геомагнитная буря) и протоны (радиационная буря) — разные явления (шкалы G и S NOAA), поэтому их вклады складываются обоснованно.
- Внешний прогноз Kp (NOAA) используется в режиме прогноза и отделён от вклада команды через сравнение с базовым подходом.

**Ограничения**
- Веса (+40 / +30 / +20 / +10) экспертные, их обоснование описано только в этом README.
- Нет собственного прогноза развития события на 6 ч: используется внешний прогноз Kp NOAA.

#### Т4. Исторический режим и временная честность (0–8)

**Реализовано**
- Исторический запрос по Kp работает на **любой** дате (архив GFZ), не только на демо-дате: проверено на 2024-06-15.
- Итоговый архив GFZ помечается как «Наблюдение (Факт)».

**Ограничения**
- Реализован только **исторический разбор** по итоговым архивам. **Прогноз из прошлого** с отсечением по времени публикации (выпуски NOAA с отметкой Issued, архив NCEI) не реализован.
- Протоны для исторических дат, кроме 11.05.2024, недоступны. Снапшот на 11.05.2024 — локальная копия значений, а не расчёт из исходных записей. В сдаваемой версии эти значения нужно подтвердить архивом GOES (NCEI) или заменить загрузкой из архива.

#### Т5. Эксперименты и проверка результата (0–6)

**Реализовано**
- Сравнение с простым подходом (только Kp ≥ 5) на одинаковых окнах — в каждом отчёте и в JSON.
- Выраженное событие: 11.05.2024 (буря G5, Kp до 9). Простой подход — 100/100 для обоих окон; модель команды — 70 и 30, то есть различает окна по наличию протонного события.
- Контрольный период: 2024-06-15 (Kp < 5) — оба подхода дают 0.

**Ограничения**
- Нет серии сохранённых расчётов и метрик (ложные тревоги, пропуски, заблаговременность).

#### Т6. Надёжность и повторный расчёт (0–5)

**Реализовано**
- Отказ источника (HTTP 403/429, таймаут, 404) не роняет приложение: срабатывает кэш или снапшот, причина пишется в лог.
- Кэш с TTL на каждый источник (TLE 12 ч, Kp 30 мин / 24 ч, протоны 15 мин, SOCRATES 1 ч), принудительное обновление, статус кэша с давностью в интерфейсе.
- Статус длительной операции отображается во время расчёта; ключи кэша включают режим и дату, поэтому параметры разных запросов не смешиваются.

**Ограничения**
- Использование снапшота видно в логах, но не помечается в интерфейсе.
- Отсутствие данных по Kp или протонам может дать 0/100 без предупреждения (см. О2) — формально «ложный вывод о благоприятных условиях».

#### Т7. Качество кода (0–4)

**Реализовано**
- Разделение по разделам: получение данных (3) → расчёт (4–5) → визуализация (6) → сценарий (7) → интерфейс (8). Интерфейс не содержит логики: `run_analysis_ui` только отображает результат `run_analysis`.
- Пороги вынесены в `THRESHOLDS`, версия — в `ALGORITHM_VERSION`.
- Секретов нет: все источники открытые.

**Ограничения**
- Один файл, нет автотестов, настройки не вынесены в конфигурационный файл или переменные окружения.

#### Т8. Документация и воспроизводимость (0–4)

**Реализовано**
- Полный код, зафиксированные версии зависимостей (`requirements.txt`), Docker-образ, запуск одной командой, пошаговая инструкция с проверкой результата и частыми проблемами.
- JSON-отчёт хранит параметры запроса, версию алгоритма и метку времени расчёта.

**Ограничения**
- В JSON нет источников, версий данных и момента отсечения — по сохранённому отчёту нельзя восстановить использованные данные.
- JSON сохраняется внутри контейнера; доступен для скачивания из интерфейса.
